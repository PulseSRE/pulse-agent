What you can do

Capabilities depend on configuration, permissions and the deployed image pair. Consult current source and operational guides.

Investigate incidents

Monitor findings and phased playbooks support crashloops, failed rollouts and scheduling failures. Investigations collect observations; missing evidence remains unresolved.

Review and approve changes

Write tools pass confirmation and configured namespace/node policy. Proactive investigations are read-only; automated monitor execution depends on server trust and supported handlers.

Measure recovery

Mutation completion and verified recovery are separate records. Postcondition probes and live readiness observations produce verified, failing or unverifiable results; recurrence can revoke a previous verdict.

Inspect installation prerequisites

Authenticated /readiness reports provider configuration, database, installation Kubernetes access and monitor state. Provider connectivity stays unknown until separately tested.

Readiness and recovery evidence

A configured provider, running monitor or successful tool request does not establish incident recovery. Live model outcomes and real-cluster acceptance are separate gates. Scheduling has a playbook, but no default scheduling auto-fix handler.

Crashloop, failed rollout and pending-pod acceptance must preserve diagnostic observations, the exact approved target/change, execution results and fresh recovery measurements. Rejected or unverifiable operations stay unresolved.
