Finds what broke. Asks before it fixes it.

Pulse Agent is an SRE and security agent for OpenShift, built on Claude. It watches your cluster, traces each incident to the change that caused it, and only acts on what you approve. Then it waits to see whether the fix held.

Why it matters

Kubernetes rarely fails in one place. One bad rollout becomes dozens of alerts, the cause lives in whoever remembers the last change, and the fix is a command typed under pressure. Pulse changes each of those.

An alert storm for one problem

One incident per cause. Pulse groups related findings and learns which ones are noise, so the page you get is the one that matters.

The cause lives in someone's head

Every incident starts from the change most likely behind it: a rollout, a config edit, an Argo CD sync, an upgrade. Pulse shows its evidence and the explanations it ruled out.

Fixes typed under pressure

A proposed fix names its target, its risk and how to undo it. You approve it; it runs as you, within your permissions, after a snapshot of what it changes.

Nobody knows if the fix held

Pulse watches afterwards and marks a fix as held only when the cluster stays healthy. If the problem comes back, the finding stays open and the fix is never turned into a skill.

Knowledge leaves with people

What a team learns stays: facts about your cluster, skills built from fixes that were verified, and past conversations you can search.

AI you can't audit

At the default trust level, every change is approved by a named person, and each can be reversed. Trust is capped on the server, protected namespaces are enforced in code, and the agent is scored in public on SRE-Bench.

On-call engineers

Fewer pages, a starting point instead of a blank terminal, and a fix that's one approval away.

Platform and SRE leads

The same response whoever is on call, runbooks that improve from real incidents, and metrics for cost and fix outcomes.

Security and compliance

Read-only by default, per-user permissions, a record of every change, and a security audit you can run any time.

What to measure: time to recover, pages per week, and changes made without a person's approval. The last one is zero by default.

Diagnose and triage

Ask in plain English; it investigates with real cluster data.

  • Crashes, OOM kills, image pull failures, scheduling problems, degraded operators
  • Correlates events, pod status, logs and Prometheus metrics into one root cause
  • 13 built-in runbooks and 83 tested PromQL recipes, checked against your cluster before use
  • Right-sizing from actual CPU and memory use against requests and limits

Audit security

A read-only security pass you can run any time.

  • Privileged containers, root users, missing security contexts, dangerous capabilities
  • Overly broad RBAC, cluster-admin bindings, wildcard permissions
  • Namespaces with no network policy, unpinned or untrusted images
  • Security context constraints and old, exposed or unused Secrets

Watch the cluster

A monitor that runs without anyone asking.

  • 32 scanners every minute: 17 for failures, 5 for stuck control loops, 5 audit, 5 predictive
  • Predicts memory, disk and autoscaler exhaustion before it happens
  • Knows each workload's normal from 7-day baselines: “3x its usual memory”
  • Learns which findings are noise and holds them back
  • A morning briefing: what happened overnight and what needs you

Explain what changed

Incidents start from the change most likely behind them.

  • Ranks rollouts, ConfigMap edits, Argo CD syncs and cluster upgrades around an incident
  • Dependency graph with blast radius, and risk scores for recent changes
  • Incident timelines that line up events across sources
  • Writes the postmortem once the incident is resolved

Fix safely

Changes are checked before, during and after.

  • Every write asks first by default, with the target named
  • Preview impact, risk and reversibility before running a fix
  • Restart, scale, rollback, pod delete and cordon check their target first, snapshot it, then confirm the result
  • Automatic fixes only at trust level 3 or above, which an admin sets on the server

Run plans

Multi-step investigations with a contract for each step.

  • Phased plans: triage, diagnose, fix, verify, each declaring what it must produce
  • A step that skips its output is retried, then marked partial, never silently passed
  • Write your own plans; every edit is versioned and reversible
  • With Temporal, plans survive restarts and wait hours for an approval

Build dashboards on request

Ask for a view and it designs one from live data.

  • 25 component kinds: metrics, tables, charts, status, topology
  • Topology in five perspectives: physical, logical, network, multi-tenant, Helm
  • SLO tracking with live error-budget burn rates
  • Capacity planning and scaling recommendations

Learn from verified fixes

Memory that only keeps what worked.

  • Remembers facts about your cluster: owners, retention, GitOps layout
  • Turns a diagnosis into a reusable skill only after its fix held
  • Refines existing skills rather than cloning them, and asks for review again

Every fix goes through four steps

Nothing skips a step. A fix that is not verified does not count, and Pulse does not learn from it.

  1. Notice

    32 scanners check the cluster every minute, from crashlooping pods to expiring certificates and SLO burn. If one lacks a permission, Pulse says so and how to fix it, instead of showing an empty list.

  2. Explain

    It ranks what changed before the incident (rollouts, ConfigMap edits, Argo CD syncs, cluster upgrades) and shows the evidence, the alternatives it ruled out, and a confidence score.

  3. Ask

    Every change waits for your approval, with the exact target named. The approval carries a one-time code, so it cannot be replayed. Ask only for a plan and no change is offered at all.

  4. Verify

    After a fix, Pulse watches the finding. Only a fix that holds for the recurrence window, 30 minutes by default, counts as verified, and only verified fixes teach it anything.

What it will not do on its own

These are enforced in code and server settings, not in the prompt, and nothing in the browser can loosen them.

Write to your cluster

Read-only unless the operator enables writes. At the default trust level, every change asks first. The server sets the highest trust level; the browser cannot raise it.

Act with more power than you have

Chat requests run with your own OpenShift token, so Pulse can only do what you are allowed to do. The monitor's background scans use the agent's own service account.

Delete pods in protected namespaces

production, openshift-* and kube-system by default. Configurable.

Drain or cordon nodes

Off unless an admin turns on the break-glass setting.

Count a fix it has not seen hold

A fix is only verified once the finding stays resolved. Before an automatic fix changes a resource, Pulse keeps a restorable copy of it.

What's new

v2.34.022 October 2026
Pairs with UI v2.34.0 and operator v0.11.0

  • Tighter security boundary. Only admins can use the tools that change the agent itself. Metrics queried from chat run with your permissions, not the agent's. Secret values are redacted before anything reaches the model.

Run it on your cluster

Pulse needs OpenShift 4.12 or later and a Claude backend: Vertex AI or an Anthropic API key. The operator installs the agent, the UI and PostgreSQL from one resource.

# After installing the operator from its catalog
apiVersion: pulse.ai/v1alpha1
kind: OpenShiftPulse
metadata:
  name: pulse
  namespace: openshiftpulse
spec:
  vertexAI: { projectId: my-gcp-project, region: us-east5, credentialSecret: gcp-sa-key }
  agent: { image: quay.io/amobrem/pulse-agent:v2.34.0, trustLevel: 2 }
  ui:    { image: quay.io/amobrem/openshiftpulse:v2.34.0 }
